# Architecture

## Principle: judgement in the model, guarantees in code

| Layer | Responsibility | Where |
|---|---|---|
| UX | `/ba-agent:start`, `status`, `review`, `triage-gaps`, `triage-ac`, `changes`; plain-language, one decision at a time | `commands/` |
| Workflow knowledge | Stage routing, gap taxonomy, criteria rules, shared non-negotiables | `skills/ba-workflow/` (+ `references/`, `references/stages/`), optional `agents/` |
| Deterministic core | State machines, identities, IST clock, audit log, schemas, requirement index, fingerprints, conflict gate, enriched-copy rendering, safe writes, validation, traceability, recovery | `scripts/ba_lib/` via `scripts/ba.py` |
| Artifacts | Authoritative JSON + rendered Markdown + append-only JSONL, plus the generated enriched copies | the project folder the user confirmed |

The model does semantic work (reading requirements, finding gaps, writing criteria, judging whether an answer is complete or contradictory) and persists everything through the core. The core **refuses** actions that would violate a rule (e.g. resolving a gap with no identity, approving the wrong version, presenting a gap with no decision owner, writing criteria for a blocked requirement), so correctness does not depend on the model remembering the rules. Hooks are not used: nothing depends on them. Subagents are optional helpers that only write JSON files; no core behaviour requires them.

Standard library only (Python ≥ 3.9; tested on 3.14): no installs, no network, no database, no MCP.

## What 2.0 is

The upstream agent already delivers well-defined requirements as Markdown, so 2.0 drops decomposition, baselines and user stories. It is a gap-finding, triage and enrichment layer: **the supplied files are the only input and are never modified; the output is a generated enriched copy of each file.**

## Modules (`scripts/ba_lib/`)

`util` (IST clock, hashing, atomic writes, path containment, identity checks) · `schema` (JSON-Schema subset validator for `schemas/*.json`) · `ingest` (Markdown reading, text normalisation, material-vs-formatting comparison, instruction-like-line scan) · `docmodel` (pure: locate requirement units in a Markdown file, render and strip the BA blocks and the header) · `reqindex` (read-only index over all files, keys, `req show` text, batches for helpers) · `snapshots` (verbatim bytes of every accepted source file) · `project` (store, state machines, audit, ID allocation, impact flagging, source protection) · `docsync` (the enriched copies: render, drift-safe refresh, `doc check`) · `gaps` (owner, gap lifecycle, answers, conflict gate, journaled closure) · `acs` + `actrack` (acceptance-criteria records, review, hashes and approved snapshots) · `changes` (detection, impact, records, reconciliation) · `checks` (validate, trace, recover, status, completion) · `conflicts` (advisory heuristics) · `present` (dialogs and cards) · `render` (+ `templates/`) · `adr` (ADR-LOG.md views) · `overview` (START-HERE.md) · `discover` (`find`) · `sync` (Cowork file bridge) · `cli`.

## Requirement identity (no atomic conversion)

A requirement *unit* is whatever the upstream document already treats as one: a heading whose text carries an ID token (default pattern covers `REQ-012`, `FR-2.1`, `AUTH-004`, `NFR-PERF-003`; replaceable with `init --locator`), or a table row whose ID cell holds one. A unit extends to the next heading of the same or higher level, or to the next unit. With no IDs anywhere in a file, each heading with text is a unit keyed by its heading path, with a warning; IDs are never inserted into the document. The key is `<relative path>::<ID>` (a second identical ID in a file becomes `<ID>#2`); the bare ID is accepted wherever it is unique. The index stores key, title, line extent, text and material hashes, the acceptance statements the document already contains (`existing_ac_hint`) and advisory duplicate flags. Heuristics (duplicates, conflicts) see the requirement text without its own ID token, so `LIB-007` does not "conflict" with `LIB-003` on the digits.

## State machines

Workflow: `INITIALIZED → SOURCE_INDEXED → GAP_ANALYSIS ⇄ WAITING_FOR_GAP_INPUT → AC_DRAFTING → WAITING_FOR_AC_REVIEW → COMPLETED`; `PAUSED`/`BLOCKED` resume only to the saved stage; later stages re-open to the gap stages when decisions or requirements change (`COMPLETED` can be re-opened). Criteria can start as soon as analysis is committed, for requirements that are not blocked. Gaps: `OPEN → WAITING_FOR_ANSWER → RESOLVED → REOPENED …`, `DEFERRED` leaves only by explicit revisit; **Carry Forward** is not a status — the gap stays `OPEN` with a `carry_forward` record (actor, decision owner, IST time, reason) that is archived to `carry_forward_history` on revisit, deferral or resolution; `RESOLVED` is reachable **only** from `WAITING_FOR_ANSWER` via `gap resolve`. Criteria: `CANDIDATE → IN_REVIEW → APPROVED | DEFERRED | CHANGES_REQUESTED`; `APPROVED → SUPERSEDED` only through a newer approved version. Tables: `project.py`.

**Live requirement status** replaces the old baseline: `READY` (no unresolved gap), `READY_WITH_OPEN_GAPS` (only carried-forward gaps) or `BLOCKED`, computed from the gaps on every call, never stored, so nothing can go stale.

## The enriched copy (design rules D2/D3)

- **Authority.** The supplied folder is read-only input (`Project._guard_source`; the project folder and `enriched/` cannot be inside it). Authoritative state is `acceptance/json/` (criteria) and `state/gap-register.json` (gaps); JSON is authoritative, Markdown is a view.
- **Pure function.** `enriched/<same relative path>` = f(accepted source snapshot, approved criteria, gap register). The renderer inserts, at the end of each requirement's extent (after the table for row units), one block fenced by `<!-- ba:begin key=… -->` / `<!-- ba:end key=… -->` with the approved criteria and approval line, an open-gaps table and a readiness line (`READY_FOR_DEVELOPMENT` / `NEEDS_CLARIFICATION` / `NOT_READY`, or `AC_PENDING` / `NOT_READY` without approved criteria). A requirement with nothing to show gets no block. A one-line generated header goes at the top (after any front matter).
- **Render from the snapshot.** The copy is built from the exact accepted bytes (`snapshots/source/`), never from the live file, so a source that changed on disk but was not yet accepted cannot misplace a block.
- **Invariant.** `strip_blocks(render(text)) == text`, byte for byte: line endings, BOM and a missing final newline included. `docsync.build_file` checks it before every write and raises `RENDER_INVARIANT_FAILED`, keeping the previous copy. Dynamic text cannot forge or close a marker (`<!--`/`-->` are escaped). A file carrying markers is refused as a source (`ENRICHED_FILE_AS_SOURCE`); a document with an unclosed code fence is copied without blocks.
- **Atomic and regenerable.** Temp file + replace, the previous copy in `state/backups/`. Because the copy can always be regenerated no write journal exists; `recover` and `doc sync` simply re-render. `state/enriched-manifest.json` records, per file, the source hash, the expected output hash and each block's hash.
- **Drift-safe refresh.** `sync_docs()` runs from `save_gaps` and `save_ac` and after every writing command. If a copy on disk differs from what was last written (a hand edit), it is **not** overwritten: `refresh` reports DRIFT and waits for `changes check`. `doc check` shows IN_SYNC / STALE / MISSING / DRIFT.
- **Hand edits.** Inside a block, a changed approved criterion is a material `MANUAL_EDIT` (kept verbatim, becomes the next `CANDIDATE`, the approved version stays in force and in the copy); any other difference (text outside the blocks, generated text, damaged markers, an unexpected block, a deleted file) is `RECORDED` and restored, the edit kept in `state/backups/`.
- **Rejected alternative.** Editing the source in place: it risks corrupting the upstream file, races with the upstream agent (worst in Cowork) and would make every enrichment look like a source change.

## Carry-forward model (MEDIUM/LOW gaps)

- **Eligibility** (`gaps.carry_forward_blocker`): priority MEDIUM/LOW, not in the policy's blocking priorities, and not `material` (security, compliance, scope/policy, critical business rules). Otherwise `CARRY_FORWARD_NOT_ALLOWED` and the existing rules apply. One shared rule, `blocks_requirements`, drives requirement status, criteria approval and the enriched copy: a *currently eligible* carried gap does not block; it blocks again if it becomes ineligible.
- **Criteria:** `open_gap_refs[]` (gap, potential impact written by the author from the gap and the requirement, readiness effect, optional interim assumption) must name **every** open gap that touches the requirement (checked on add, edit, approve and confirm-unaffected). `readiness` is derived; interim assumptions are rendered as *not approved* and never become decisions.
- **Resolution loop:** `gap revisit`/`gaps next --carried` → normal validated resolution → `apply_closure` flags every criteria record listing the gap (any folder) → `ac edit` (new version, re-review). `confirm-unaffected` is refused while a record still names a resolved gap; a gap opened later flags existing records the same way.
- **Visibility:** `status`, `trace` (open-gap → criteria table, records missing a link), the gap/criteria Markdown, the open-gaps table in the enriched copy, `complete` (a `NOT_READY` record keeps the workflow PARTIAL; carried gaps are always listed).

## Triage commands

`triage-gaps` and `triage-ac` are orchestration only; they add no business rules and no agents (the gap-analyst / ac-writer agents generate content and are not involved in reviewing it).
- **List** (read-only, derived from the files on every call, so resume needs no extra state): `gaps triage` = unresolved gaps that are `OPEN` (incl. `WAITING_FOR_ANSWER`, reopened, answer-later, carried forward) or `DEFERRED`; `ac triage` = records in `candidates/`, `unapproved/`, `deferred/`, each with `eligible` / `blockers` computed from the same rules `ac approve` enforces (impact review, changed requirement text, blocking gaps).
- **Preflight:** `ac triage` reports problems that block every record once (`preflight`: an unreviewed requirement change); a record flagged by a resolved gap offers `Update criteria` with the decision to apply.
- **Present one:** `gaps next --id` (OPEN → `WAITING_FOR_ANSWER`; DEFERRED and carried-forward gaps are returned unchanged, because looking must not change state), `ac next --key` (any pending folder).
- **Act:** only existing actions — `gap answer / explain / defer / carry-forward / revisit / resolve`, `ac approve / edit / defer / request-changes / revisit` — plus two audit-only "keep" actions (`gap keep`, `ac keep`). A deferred or carried gap needs `gap revisit` before it can be answered; a deferred or not-approved record needs `ac revisit` before it can be approved (same version, audited). `ac edit` always creates a new CANDIDATE version.

## Change detection and impact analysis

**Baselines for comparison.** `init` stores the exact bytes of each requirement file (`snapshots/source/<file>@v1.md`, index with file hashes). Accepting a change or a formatting-only change appends the next version. Each `ac approve` records, in `snapshots/ac/index.json`, the material hash (criteria, declared open gaps, assumptions, notes), the content hash, an approval/readiness hash and an immutable copy of exactly what was approved; the audit event `AC_APPROVED` carries the hashes. Each criteria record is pinned to the material hash of the requirement it was written for.

**Material vs formatting-only.** `ingest.material_normalize` drops Markdown emphasis/heading/list/table markup, line wrapping, repeated whitespace and typographic quotes; words, numbers, case and punctuation inside a sentence stay. A requirement whose normalised text is unchanged is `FORMATTING_ONLY`; a file whose every requirement is unchanged in meaning (including edits outside the requirements) is accepted by the core itself, re-indexed and re-rendered, recorded as `RECORDED` and audited; nothing is flagged.

**Detection (`changes.detect`, read-only).** Source: each file is re-read and its units compared **by key** (`added` / `removed` / `changed` / `formatting_only`; `added_files` / `removed_files`), with line-level hunks between the snapshot and the new text; a renamed ID shows as removed + added (no old→new mapping). Approved criteria: for every file in `acceptance/approved/` and every tracked record, compare with the tracked hashes; classes `MANUAL_EDIT`, `APPROVAL_ALTERED`, `DELETED`, `UNREADABLE`, `UNTRACKED_APPROVED`, `FORMATTING_ONLY`. Enriched copies: each file against the manifest's expected hash (see the enriched-copy rules above). Unreadable files or files carrying BA markers assess nothing and say so.

**Impact.** Source: changed or removed requirements, new requirements, open gaps and confirmed decisions on them (listed for re-validation, never invalidated), linked and approved criteria, the workflow stage it will reopen. Criteria: fields changed, criteria added/removed, open gaps on the requirement, the approval on record.

**Records and lifecycle.** `changes/json/CHG-nnn.json` + `changes/md/CHG-nnn.md` + `changes/json/change-register.json` (schema `change`, types `SOURCE_CHANGE` and `AC_CHANGE`). `DETECTED` (explained, nothing downstream touched) → `APPLIED` (`changes apply`: named person + their words; the new source accepted — snapshots, index, enriched copies; criteria of changed/removed requirements `impact_review`, their gaps `needs_impact_review`, gap analysis marked incomplete, workflow reopened to `GAP_ANALYSIS`; for an edited approved criterion the approved version stays in force, the verbatim edit is kept in `snapshots/ac/…observed-CHG-nnn.*` and becomes the next `CANDIDATE`) → `RECONCILED` when every item (`requirement`, `new_requirement`, `gap`, `ac`, `reapproval`, `ac_removal`) is done — closed by the real work, evaluated from live artifacts (`reconcile`, run after every command) or dismissed with a reason (`new_requirement`, `ac_removal` only). Also `RECORDED` (formatting-only, restored copies, the BA Agent's own `ac edit`), `SUPERSEDED` (changed again before applying), `REVERTED` (file put back). Re-detection is idempotent (`dedupe_key`).

**Where it runs.** `status` shows it read-only; `changes check` records. `guard` runs inside the CLI before `gaps add|commit|next`, `gap resolve` and `ac add|next|approve|edit` and refuses with `CHANGES_UNREVIEWED` while a material change is unreviewed; `gaps triage`, `ac triage`, `complete`, `report` run the check and attach `change_check`; the start/review/changes commands and the resume guide call it first. `complete` stays PARTIAL while any record is unreviewed or has open items. `validate` warns about unreviewed changes, drifted approved records, hand-edited copies and damaged snapshots; `trace --write` adds a *Change impact* section.

**Guarantees.** The requirement files are only read; the accepted fingerprint changes only at `changes apply` (or a recorded formatting-only acceptance); a manual edit is preserved byte for byte before anything else is written; approved versions, approvals and decisions are never deleted or invalidated without a recorded reason (`ac history` lists every approved version, approver, wording and snapshot); version numbers of criteria are never reused.

## Gap closure protocol (crash-safe)

1. Validate everything (owner, identities, answer complete, conflict gate, materiality, clock) — no writes yet.
2. Write `state/pending/<id>.closure.json` (the full plan: decision, audit event, new gap record, requirements the decision contradicts).
3. Apply idempotently: append decision → append `GAP_RESOLVED` audit event (same `event_id`) → **gap register (atomic replace)** → rendered files → impact propagation (criteria flagged, enriched copies re-rendered) → delete journal.
4. A crash at any point leaves the journal; `validate` flags it, `recover` rolls forward without duplicating the decision or event; retries are refused with `CLOSURE_IN_PROGRESS`. `validate` also cross-checks every `RESOLVED` gap against its decision and audit event.

## Conflict handling

Every answer is compared (advisory, deterministic) with requirement text, active decisions and earlier accepted answers: numeric disagreement, negation polarity, opposing terms. Candidates must be explicitly reviewed (`--reviewed`) before `PASSED`; a recorded conflict blocks `PASSED`; a confirmed change (`CHANGE_CONFIRMED`) needs a named authoriser and a verbatim statement; it supersedes contradicted decisions, reopens gaps closed by them and flags the criteria of the affected requirements. A requirement among the contradicted artifacts is **not** edited (it belongs to the upstream document): the result lists it as `upstream_change_required` and an `UPSTREAM_CHANGE_REQUIRED` audit event is written. The heuristic is a safety net, not a semantic judge — the model and human decide.

## Context engineering

Principle: the model receives *the right information, only when it is needed*, and the core does everything that does not need judgement.
- **Load on demand.** `ba-workflow` is the only listed skill: the router and the non-negotiables. Each stage is a short loop in `references/stages/<name>.md`, opened only for the current stage. Branch detail sits beside it and is opened only at the branch (`stages/gap-resolution/{actions,validate-and-resolve,revisit,triage}.md`, `stages/ac-review/triage.md`). `change-detection` loads only when `changes check` reports a change. `tests/test_context` fails if a skill grows past its budget or a reference pointer dangles.
- **Presentation in code (`ba_lib/present.py`).** One gap or record at a time. The core builds the `AskUserQuestion` payload (`dialog`) and the compact markdown (`card`); the numbered `fallback` is built only with `--fallback`, after the dialog tool failed. The model relays. A gap whose dialog holds everything is `inline` — sent as the dialog alone; a criteria record always sends its card first because the requirement and the criteria must be read to be approved. Queues are a one-line `summary`.
- **Right fields, right time.** The gap packet keeps what the model *acts on*; `gap explain` carries the plain-language facts (fetched only if the human asks), `ac next` carries a *Decision to apply* only for a record flagged by a resolved gap, `ac show` / `--full` the raw record only when an edit file is needed. `req show` returns one requirement; nobody opens the requirement files.
- **Hoisted blockers.** `ac triage.preflight` states what blocks every record once, so the user is never walked through records that cannot be approved when one step unblocks them all.
- **Compact output.** One-line JSON, empty values omitted, `files_saved` limited to the folders a command changed (a fresh disk scan taken after the write, which is also the save check).
- **Delegation (optional).** `source index` / `init` return per-requirement sizes, `batches` (≤ 30k characters of requirement text) and `delegate` (> 60k characters; `--delegate-above`, `--batch-chars` or `BA_DELEGATE_ABOVE`, `BA_BATCH_CHARS` override). Helpers (`gap-analyst`, `ac-writer`) start cold and re-read their batch, so the model asks once and otherwise reads requirement by requirement. Helpers return ≤ 8 lines plus a file under `state/inbox/`; only the main session runs mutating commands. With no decomposition step, the heaviest token consumer of 1.x is gone.
- **Generated help.** `help` is built from the argparse definitions, so there is no static CLI reference to drift.
- **Cowork file bridge.** `--changed-files` reports every file a command wrote, moved or removed (a before/after tree comparison, so every writer is covered); `manifest` compares a staged copy with the last committed state, `manifest --stage-list` names the lean set to stage (state, snapshots, `json/` records and `enriched/`), and `bridge on` makes the report the default (`ba_lib/sync.py`, `references/cowork-sync.md`). The requirement files are staged in as input and never committed back; what is committed back is the project folder and `enriched/`, so there is no write race with the upstream agent. Backups and `state/inbox/` are never synced. An `--enriched-dir` outside the project folder is not covered by this bridge.

## Safety

Requirement content is data: instruction-like lines are flagged (advisory) and no code path acts on requirement text. Writes go through `safe_join` (relative paths only, `..`/absolute/drive/symlink escapes rejected), the supplied requirement files are write-protected, writes are temp+replace with a rolling `.bak`, `safe_write.py` only writes under `state/inbox/` and `reports/`. Identities must come from the user (placeholder names like "Claude"/"unknown" are rejected; the code cannot prove a person is real). A 1.x project is refused with `LEGACY_PROJECT` rather than guessed at. The core does not claim to be a sandbox.
